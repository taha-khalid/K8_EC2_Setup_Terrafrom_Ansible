# AWS Multi-Node Kubernetes Cluster with Terragrunt, Ansible & Cilium CNI

An end-to-end, automated Kubernetes cluster deployment on AWS using **Terraform**, **Terragrunt**, **Ansible**, and **Cilium CNI**.

This project automates the complete lifecycle of a Kubernetes environment, including:

* Provisioning AWS network and compute resources
* Dynamically scaling control-plane and worker nodes
* Configuring the host operating systems
* Installing and configuring `containerd`
* Initializing a Kubernetes control plane with `kubeadm`
* Dynamically joining worker nodes to the cluster
* Deploying Cilium eBPF networking
* Maintaining isolated Terraform remote state
* Automatically handing infrastructure provisioning over to Ansible

# ✨ Key Engineering Features

## 1. Dynamic Scaling via `env.hcl`

Node counts are centrally managed in:

```text
live/dev/env.hcl
```

Example:

```hcl
locals {
  environment           = "dev"
  master_instance_count = 1
  worker_instance_count = 2
}
```

Child Terragrunt units read these values dynamically using:

```hcl
read_terragrunt_config(
  find_in_parent_folders("env.hcl")
)
```

This allows the cluster capacity to be changed from a single configuration file.

For example, increasing:

```hcl
worker_instance_count = 2
```

to:

```hcl
worker_instance_count = 4
```

allows four worker instances to be provisioned without modifying the worker deployment module itself.

---

## 2. Fully Automated Infrastructure-to-Ansible Handoff

The `ansible_bootstrap` Terragrunt unit uses a local `null_resource` and an `after_hook` to automatically transition from infrastructure provisioning to configuration management.

After the EC2 instances are created, the bootstrap workflow:

1. Collects the public IP addresses of control-plane and worker nodes.
2. Generates `ansible/inventory.ini`.
3. Assigns predictable hostnames such as:

   * `master-1`
   * `worker-1`
   * `worker-2`
4. Polls TCP port `22` until the SSH daemons become available.
5. Executes the Ansible playbook.
6. Configures the Kubernetes nodes.
7. Initializes the control plane.
8. Joins the worker nodes.
9. Deploys Cilium CNI.

This creates an automated pipeline from AWS infrastructure provisioning to a functional Kubernetes cluster.

---

## 3. Dynamic In-Memory Join Token Distribution

During the control-plane provisioning stage, `kubeadm init` generates the command required for worker nodes to join the cluster.

The generated join command is captured and registered as an Ansible fact.

Worker nodes retrieve the command dynamically through `hostvars` during the worker provisioning stage.

```text
Control Plane
     │
     │ kubeadm init
     ▼
Generate Join Command
     │
     │ Ansible Fact
     ▼
   hostvars
     │
     ▼
 Worker Nodes
     │
     │ kubeadm join
     ▼
Kubernetes Cluster
```

This approach avoids hard-coding the cluster join command in the inventory or repository.

---

## 4. Non-Overlapping Cilium Pod CIDR Architecture

The Kubernetes Pod network is intentionally separated from the AWS VPC network to avoid routing conflicts.

| Network                 | CIDR            |
| ----------------------- | --------------- |
| **AWS VPC**             | `10.0.0.0/16`   |
| **Cilium Pod CIDR**     | `10.244.0.0/16` |
| **Native Routing CIDR** | `10.0.0.0/16`   |

The separate Pod CIDR prevents Kubernetes Pod networking from overlapping with the underlying AWS VPC address space.

This is particularly important when Cilium creates host networking interfaces and routes such as `cilium_host`.

---

## 5. Systemd Cgroup Driver Alignment

Containerd is configured with:

```toml
SystemdCgroup = true
```

This aligns containerd's cgroup driver with kubelet's systemd cgroup configuration.

Using the same cgroup driver across the container runtime and kubelet helps avoid node instability and runtime-related issues caused by mismatched cgroup configurations.

# 🔒 Network & Security Specifications

The infrastructure provisions dedicated AWS Security Groups for Kubernetes and Cilium communication.

| Port / Protocol | Direction | Source / Destination    | Purpose                          |
| --------------- | --------- | ----------------------- | -------------------------------- |
| `22/TCP`        | Inbound   | Administrative CIDRs    | SSH access                       |
| `6443/TCP`      | Inbound   | Control plane / Workers | Kubernetes API Server            |
| `10250/TCP`     | Inbound   | Intra-cluster nodes     | Kubelet API                      |
| `2379-2380/TCP` | Inbound   | Control-plane nodes     | etcd client / peer communication |
| `8472/UDP`      | Inbound   | Intra-cluster nodes     | Cilium VXLAN overlay networking  |
| `4240/TCP`      | Inbound   | Intra-cluster nodes     | Cilium health monitoring         |

### Security Considerations

For production environments:

* Restrict SSH access to trusted administrative CIDRs.
* Restrict Kubernetes API access to required clients and cluster components.
* Restrict `10250/TCP` to trusted cluster nodes.
* Never expose etcd ports `2379-2380` publicly.
* Restrict Cilium VXLAN traffic to cluster nodes.
* Avoid exposing unnecessary Kubernetes ports to the public Internet.

# 🚀 Deployment Guide

## 1. Navigate to the Environment

Navigate to the target environment:

```bash
cd live/dev
```

---

## 2. Initialize the Terragrunt Stack

Initialize all Terragrunt deployment units:

```bash
terragrunt run --all init
```

This initializes the Terraform modules and configures their remote state backends.

---

## 3. Deploy Infrastructure & Bootstrap Kubernetes

Execute the complete deployment:

```bash
terragrunt run --all apply
```

Terragrunt resolves the configured dependencies and provisions the infrastructure in the appropriate order.

The deployment flow is:

```text
VPC
 │
 ▼
Security Groups
 │
 ├───────────────┐
 ▼               ▼
Master Nodes   Worker Nodes
 │               │
 └───────┬───────┘
         │
         ▼
Ansible Bootstrap
         │
         ▼
Kubernetes Cluster
         │
         ▼
Cilium CNI
```

Once the infrastructure is ready, the `ansible_bootstrap` workflow automatically invokes the Ansible deployment.

# 🔍 Verifying the Cluster

Once the Ansible bootstrap process completes successfully, connect to the control-plane node.

## 1. SSH into the Control Plane

```bash
ssh -i ~/.ssh/k8s-key.pem ubuntu@<MASTER_PUBLIC_IP>
```

---

## 2. Check Node Status

Run:

```bash
kubectl get nodes -o wide
```

Expected output:

```text
NAME       STATUS   ROLES           AGE   VERSION   INTERNAL-IP   EXTERNAL-IP
master-1   Ready    control-plane   5m    v1.35.0   10.0.1.x      <none>
worker-1   Ready    <none>          3m    v1.35.0   10.0.1.y      <none>
worker-2   Ready    <none>          3m    v1.35.0   10.0.1.z      <none>
```

All nodes should eventually reach:

```text
STATUS: Ready
```

---

## 3. Verify Cilium eBPF Status

Check the Cilium deployment:

```bash
cilium status
```

Run the Cilium connectivity test:

```bash
cilium connectivity test
```

The connectivity test validates networking between workloads across the Kubernetes cluster.

# 🧹 Teardown

To destroy the complete AWS infrastructure:

```bash
cd live/dev

terragrunt run --all destroy
```

> **Warning:** This permanently destroys the infrastructure managed by the environment. Make sure any required data or resources have been backed up before running the command.

find . -type d -name ".terragrunt-cache" -prune -exec rm -rf {} +
